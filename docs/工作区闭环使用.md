# 工作区闭环使用

这份说明对应已实现的单工作区闭环：首次引导→明确命名→每轮读取→原话保存→公开回复保存→有来源的认识→新对话接续。

## 用户如何开始

源码用户在项目目录先安装依赖并编译，然后初始化一次：

~~~powershell
npm ci --ignore-scripts
npm run build
node dist/cli/main.js workspace-init
~~~

初始化完成后，用户无需重复命令，也无需自己整理数据库；在能够读写工作区、遵守AGENTS的智能体里开始日常对话，按提示用“给你起名：名字”提交名字即可。

已安装npm包的接入者也可执行 soul-core workspace-init --workspace <自己的工作区>。该目录需已存在；本版初始化只使用其中data/soul，不提供跨工作区绑定或自动同步。

初始化创建以下本地内容，不覆盖原有AGENTS规则，也不自动命名、导入聊天或迁移旧身份：

| 内容 | 用途 |
| --- | --- |
| AGENTS.md的soul-core标记段 | 提醒宿主每次日常对话执行引导；源码维护继续遵守原规则 |
| .soul/GUIDE.md | 本机核心入口、首次命名和每轮读写步骤 |
| .soul/workspace.json | 固定身份ID与工作区内的档案位置 |
| data/soul | 权威人生档案，关闭窗口后仍然保留 |
| .gitignore的私有目录规则 | 排除.soul与人生档案，供他人克隆独立模板 |

如果data/soul已经存在，会接续并固定其身份ID；不会按名字重新创建。重复初始化保留同一ID，刷新指南与入口，不重复追加AGENTS段。

## 宿主需要做的事

命令行返回JSON，也可使用导出的SoulWorkspace接口。正文通过UTF-8 JSON文件或标准输入传入，不把长对话拼成shell代码。

1. 每次新对话或压缩后：workspace-open，读取rules和context.text，替换旧快照。
2. 每次真实用户输入提交：workspace-receive，使用稳定sessionId/messageId和原话；返回本轮sourceId与新快照。未命名时只有明确命名才会出生。
3. 用宿主已有模型生成回答；回忆较早资料时按需workspace-recall，再用workspace-read展开原件。
4. 完整回复实际公开后：workspace-reply，提交真实回复和inReplyTo来源ID。模型失败时只保留已经提交的用户原话，不伪造回答。
5. 有值得延续的新认识或未完话题时：workspace-record，保存模型的解释以及可核对的引文；没有新认识时只记原话即可。

具体JSON格式与本机调用参数在.soul/GUIDE.md。对话框重开无需调用新建或重新命名，只重新open。

源码维护、调试、模型配置和产品方案讨论不记为她的生活；混合消息只取明确的日常部分，不自动导入本项目历次开发对话。工具输出、系统提示、草稿、模型原始思考和中断片段也不作为她的公开经历。

**工作区说明是宿主协议，不会给封闭聊天平台凭空增加生命周期钩子。** 能读写工作区的智能体可以按指南执行；其他宿主需由接入者把提交、公开回复与重开事件接到这些接口。宿主未完成记录时不能声称已经记住。本版没有新增聊天前端、后台守护进程或内置模型。

## 一个人生，有限上下文

当前快照包括固定身份、真实出生时长、发展阶段、模拟情绪、当前理解、兴趣与相关经历。普通6000字符、复杂回忆12000字符，显式可调；完整原话仍保存在本地并可按ID展开。

未结束的话题和自我认识优先进入下一次快照。理解变化以revisesId串联，保留过去理解，不用新摘要覆盖整个人生。单次模型上下文仍有限，接续通过持久档案和按需回忆实现。

## 失败时怎样处理

- 已绑定的数据库缺失：报错，恢复原档案；不会悄悄新生。
- 身份ID与绑定不符：报错，检查原目录与绑定；不会按同名换人。
- 同一消息重试：返回原记录；同ID更换正文会拒绝覆盖。
- 被隐私清除的消息再次提交：拒绝复活；已清除来源不能再用于提交公开回复。
- 模型生成或写回失败：明确报告，已保存用户原话继续保留；宿主用相同消息标识重试。

对话写入是否真实公开，由宿主负责；核心检查消息身份、会话、来源、引文与去重，不能证明宿主没有伪造内容。隐私管理、加密迁移和旧身份接续继续使用独立管理命令，不加入普通陪伴工具。

## 已验证与可选扩展

使用虚构档案验证了从等待命名到关闭重开、跨会话恢复、公开回复和有来源理解、认识修正、故障与隐私重放；生产npm包也验证同一套CLI在独立安装后的完整往返。

跨工作区接续、跨设备同步、访问范围、语义检索增强、自动整理与形象绑定的选择，统一放在[扩展方案](工作区连续性与跨工作区绑定.md)。它们不阻塞这条基本闭环，也不默认启用。
